# メンバーの追加・管理 設計書

参照元：マネーフォワード クラウド給与「メンバーの追加・管理」画面（ホーム画面「メンバー管理」カードからの遷移先）
取得画面：3枚（メンバー一覧／メンバー情報変更モーダル／メニュードロップダウン）

> ⚠️ 「従業員をメンバーに追加する」「給与担当者を追加する」等、メニューから実際に遷移した先の入力フォーム画面は今回未取得です。追加フローの詳細設計にはそれらの画面キャプチャが別途必要です（8章参照）。

## 1. 画面概要

| 項目 | 内容 |
|---|---|
| 画面名 | メンバーの追加・管理 |
| 目的 | システムにログインできるアカウント（メンバー）の一覧表示・権限確認・追加・編集を行う |
| 主要ユーザー | 給与担当者（管理者権限） |
| 表示トリガー | ホーム画面「メンバー管理」カード → 「メンバー追加」リンク、サイドナビ「基本設定」配下 想定 |

「メンバー」＝システムへのログインアカウントであり、「従業員」＝給与計算対象の人事マスタデータという、2つの概念が分かれている点が設計上の重要ポイント（4章参照）。

## 3. コンポーネント仕様

### 3-1. メンバー一覧テーブル

| 列 | 内容 | 備考 |
|---|---|---|
| 権限 | 例：給与担当者 | ロール名を表示 |
| 氏名 | 例：中澤雄一郎(自身) | 自分自身の行は「(自身)」を付記 |
| メールアドレス | ログインID相当 | |
| 従業員番号／紐付く従業員 | 空欄あり | メンバーと従業員マスタの紐付け状況を表示する列（見出しが2行になっている＝2情報を1列にまとめている可能性、要実機確認） |
| ログイン状況 | 空欄あり | 招待中／ログイン済み等のステータスが入る想定（本キャプチャでは空） |
| 操作 | 「変更」ボタン | 行ごとに配置 |

- 表示件数セレクタ（25件など）をテーブル上下に配置（同一コントロールを2箇所に重複配置している＝長い一覧をスクロールしても操作しやすくする意図）

### 3-2. 「メニュー」ドロップダウン

| メニュー項目 | 想定機能 |
|---|---|
| 従業員をメンバーに追加する | 既存の従業員マスタに対してログインアカウントを発行する |
| 給与担当者を追加する | 従業員に紐付かない管理者アカウントを追加する（社労士・管理部門など従業員ではないログインユーザー向け） |
| 従業員CSVをダウンロードする | メンバー一覧または従業員一覧をCSVエクスポート |
| 従業員CSVをアップロードする | CSVによる一括登録・更新 |

→ 「メンバー追加」には**2種類の追加経路**がある点が設計上のポイント：
  1. 従業員起点（既存の従業員データにログイン権限を付与）
  2. アカウント起点（従業員データを持たない担当者アカウントを直接作成）

> 📌 **公式サポートサイトでの補足確認**（[従業員のログイン方法](https://biz.moneyforward.com/support/payroll/guide/login/lo01.html)、[給与担当者の設定方法](https://biz.moneyforward.com/support/payroll/guide/login/lo02.html)より）：
> - 「従業員をメンバーに追加する」：入力項目は**従業員のメールアドレス**（複数人まとめて入力可）＋**権限選択**で、「一括追加」ボタンで確定する。CSVファイルによる一括招待も可能と記載あり（フォーマット等の詳細は記事に記載なし）。権限選択で「給与担当者」を選ぶと、従業員と給与担当者を1人で兼務させることも可能。
> - 「給与担当者を追加する」：入力項目は**名前**＋**メールアドレス**のみ。登録後、完了メッセージが表示される。
> - いずれの経路でも、招待された相手には「パスワードを設定してください（マネーフォワード クラウド給与）」という件名のメールが自動送信される（既に他のマネーフォワードサービス利用者の場合は「【マネーフォワード クラウド給与】●●（事業者名）のメンバーへ招待されました」という件名になる）。招待先はメール内URLからパスワード設定→アカウント確認→規約同意の順で初回ログインを行う。
> - これにより8章「未取得・要追加確認事項」の該当項目（フォーム画面の入力項目）はテキストレベルでは一部判明した（画面キャプチャそのものは依然未取得）。

### 3-3. メンバー情報の変更モーダル

| フィールド | 型 | 備考 |
|---|---|---|
| 氏名 | text | 一覧の「変更」ボタン押下で表示されるモーダル。今回のキャプチャでは氏名のみ編集可能項目として表示 |

- モーダルはオーバーレイ（背景を半透明の黒でディム）＋中央配置の白カード
- フッターに「更新」（オレンジ・ゴールド、主アクション）／「キャンセル」（グレー、副アクション）
- 右上に「×」で閉じるアイコン

※ 実際には氏名以外に権限変更・メールアドレス変更等の項目がある可能性が高いが、今回のキャプチャでは氏名編集モーダルのみのため、他項目は未確認（8章参照）。

## 4. データ構造（登録内容）

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| member_id | id | ○ | メンバー（ログインアカウント）の識別子 |
| role | enum | ○ | 権限種別（例：給与担当者。他ロールの有無は未確認） |

> 📌 **公式サポートサイトでの補足確認**（[「権限パターンの追加・管理」の設定方法](https://biz.moneyforward.com/support/payroll/guide/system-management/pa_office_authority_patterns.html)より）：`role`は単純な固定enumではなく、**権限パターン**という別マスタで管理されている。
> - 権限パターンには「全権管理者向けパターン」（既定で用意され編集・削除不可）と、ユーザーが作成する「カスタム権限パターン」の2種類がある。
> - 各パターンは、給与計算・賞与計算・従業員情報・基本設定・支払業務など業務系7項目と、システム管理・メンバー管理というシステム系項目それぞれについて、「閲覧不可／閲覧可／編集可」の3段階権限を個別に設定できる。
> - 権限パターンの割り当ては「メンバーの追加・管理」画面（＝本画面）からメンバーを選択して行う、と記事に明記されている（給与担当者権限のメンバーのみが対象）。ただし、割り当てUIが本画面のどこに存在するか（3-3章の「変更」モーダル内か、別の操作か）までは記事に明記されておらず、依然として実機確認が必要。
> - 権限パターンが割り当て中の場合は削除不可という制約もある。
> - 自社実装では、`role`を固定enumにするか、上記のような「権限パターン（業務項目×権限レベルのマトリクス）」テーブルとして別途正規化するか、方針決定が必要。
| name | string | ○ | 氏名 |
| email | string(email) | ○ | ログインID／通知先メールアドレス |
| employee_id | id (nullable) | - | 紐付く従業員マスタのID（担当者アカウントの場合はnull） |
| login_status | enum | - | 招待中／ログイン済み等（値の種類は要実機確認） |
| is_self | boolean | - | 自分自身の行かどうか（表示上「(自身)」を付与する判定用） |

## 5. デザインルール

### 5-1. 配色・共通ルール

- ヘッダー・サイドナビはホーム画面（[[01_ホーム画面_設計書]]相当）と共通仕様を踏襲
- テーブルヘッダー行：薄いグレー背景、グレー文字
- 「変更」ボタン：カーキ〜グレー系のセカンダリボタン（一覧画面の「メニュー」ボタンと同系色）
- モーダル主アクション（更新）：オレンジ〜ゴールド（初期設定チュートリアルの「次へ」ボタンと同系色で統一されている＝サービス全体の主アクションカラーとして採用されている可能性が高い）
- モーダル副アクション（キャンセル）：薄いグレー背景

### 5-2. テーブルルール

- 列見出しは項目名のみのシンプル表示、2行にまたがる見出し（従業員番号／紐付く従業員）は関連情報をまとめて1列にする際のパターンとして踏襲可
- 空データはブランク表示（「未設定」等のプレースホルダー文言は使用していない）
- 行アクションは右端に統一配置

### 5-3. モーダルルール

- 幅は画面中央に小さめ固定（編集項目が少ない場合は最小限のサイズ）
- タイトル＋×閉じるボタンをヘッダーに配置
- フォームは「ラベル：入力欄」の横並び（他画面と統一）
- フッターに主／副ボタンを横並び、主ボタンを左に配置

## 6. 「従業員」との関係整理（設計上の要注意点）

マネーフォワード クラウド給与では、**「従業員（給与計算対象の人事データ）」と「メンバー（システムログインアカウント）」が別概念**として設計されている。

- 従業員データが先に存在し、そこにログイン権限を後付けする（＝Web給与明細を従業員自身に見せる運用）
- 従業員データを持たない「給与担当者」（社内の労務担当・顧問社労士など）も別途アカウント作成できる

自社勤怠システムに実装する際は、既存の「従業員マスタ」と「アカウント（ログインユーザー）」の関係が既にどうなっているかを確認し、この2軸構造を流用するか、1つのテーブルに統合するかを先に方針決定することを推奨。

- 本画面はホーム画面・初期設定チュートリアルと同じ配色・ボタンスタイルを踏襲しているため、共通コンポーネント（ボタン、テーブル、モーダル）として一元管理するのが望ましい
